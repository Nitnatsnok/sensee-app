# Codex Local Environment

Use this page to configure OpenAI Codex App for this repository without duplicating the shared agent rules.

## Instruction Source

Codex should read repository instructions from `AGENTS.md` and nested `AGENTS.md` files. Project skills live in `.agents/skills` and are cataloged in `docs/agents/skills.md`.

Do not create Codex-only copies of these rules.

## Local Environment Setup

Official Codex App docs describe Local Environments as project settings for worktree setup scripts and common actions. The app stores generated shared configuration in `.codex/` at the project root, and that file can be checked into Git for the team.

This repository commits the project Local Environment config at:

```text
.codex/environments/environment.toml
```

The committed file carries a generated `THIS IS AUTOGENERATED. DO NOT EDIT MANUALLY` header. Treat it that way: regenerate it through the Codex App and review the generated output against this project policy before committing. Do not hand-edit it or hand-invent undocumented TOML shapes.

The committed generated file exposes one automatic `[setup].script`:

```shell
python3 scripts/agents/setup-local-env.py
```

This single command is cross-platform: the setup logic lives in one Python script in `scripts/agents/`, so the same `[setup].script` works on macOS, Linux, and Windows, provided `python3` is on `PATH`.

`scripts/agents/setup-local-env.py` runs only lightweight setup and `Gradle help`.

The `[[actions]]` entries are single cross-platform commands with no per-platform
`platform` fields. Do not hand-invent undocumented TOML fields such as
`[setup.<platform>]`; let the Codex App regenerate the file and review the output
against this policy before committing.

Current automatic setup decision:

| Option | Decision | Reason |
| --- | --- | --- |
| Cross-platform `python3` setup command | Current policy | One Python script in `scripts/agents/` runs the same way on every platform, so a single `[setup].script` works everywhere without platform-specific automatic setup. |
| Platform-specific automatic setup fields | Not committed | No longer needed now that setup is cross-platform; the TOML override shape is also not documented by Codex. |
| Separate committed environments per platform | Not committed | No official or generated evidence in this repository confirms multiple committed environment files per platform. |

The config intentionally omits `[cleanup]`.

Cleanup decision:

- `scripts/agents/setup-local-env.py` prepares the worktree, writes only ignored `local.properties` inside the worktree when an Android SDK is detected, may adjust `./gradlew` executability on Unix, and runs Gradle `help`.
- Gradle may populate normal user-level Gradle caches, but those caches are not project-owned resources and must not be removed by a repository cleanup action.
- There is no emulator, device, server, background process, temporary external service, or project-owned external resource to clean up.

Do not add cleanup just because a generated example contains a placeholder. Add `[cleanup]` only if a future setup step creates a concrete project-owned resource and the Codex environment schema still supports cleanup for that use case.

## MCP Servers

Codex MCP servers are configured in the project-scoped `.codex/config.toml`.
Codex does not read the Claude-style `.mcp.json` file for MCP setup.

The committed Codex config exposes:

- `graphify` — `uv run --with graphifyy python -m graphify.serve graphify-out/graph.json`
- `likec4` — `npx -y @likec4/mcp` with `LIKEC4_WORKSPACE=docs/c4`

The project must be trusted for Codex to load `.codex/config.toml`. The MCP
commands run with `cwd = ".."` because the config file lives in `.codex/` and
the servers expect paths relative to the repository root.

## Actions

| Action | Command (all platforms) |
| --- | --- |
| Setup Local Env | `python3 scripts/agents/setup-local-env.py` |
| Gradle Tasks | `python3 scripts/agents/list-tasks.py` |
| Validate Fast | `python3 scripts/agents/validate.py fast` |
| Validate Docs | `python3 scripts/agents/validate.py docs` |
| Validate Architecture | `python3 scripts/agents/validate.py architecture` |
| Gradle Check | `python3 scripts/agents/validate.py full` |

Prefer module-scoped Gradle tasks from `AGENTS.md` when a change is narrow.

The `Gradle Check` action runs `python3 scripts/agents/validate.py full` (the full root `check`). It is a deliberate explicit action only and is not part of setup.

## Aggregate Verification Decision

Current root Gradle tasks include `check` and `konsistCheck`. There are no project-level `verify`, `verifyDocs`, or `verifyArchitecture` tasks yet.

Decision: do not add new Gradle aggregate tasks in this agent-environment pass. `validate.py` maps its `full` and `architecture` modes directly to the existing `check` and `konsistCheck` tasks. Adding `verify` / `verifyDocs` / `verifyArchitecture` remains future deliberate build-logic work, not an unresolved setup blocker.

## Worktrees

Codex App worktrees use Git worktrees. Each worktree has its own file checkout, so ignored local files such as `local.properties` are not carried over automatically.

The setup script regenerates `local.properties` from `ANDROID_HOME` or `ANDROID_SDK_ROOT` when an Android SDK directory is available. If the directory lacks common SDK markers such as `platforms/` or `cmdline-tools/`, the script warns but still writes the ignored file. If neither variable is set, the script warns and continues.

Use Codex Handoff when moving a thread between Local and Worktree. Codex handles the Git movement between the two checkouts, but ignored files do not move with the thread. Before handoff, keep generated files, secrets, and local-only settings out of Git.

## Future Codex Config Changes

Future Codex App updates may generate additional `.codex` files or modify `.codex/environments/environment.toml`.

Decision: generated Codex config changes must be reviewed before committing:

- no machine-specific paths;
- no secrets;
- project MCP servers stay in `.codex/config.toml`;
- setup/actions call `scripts/agents/`;
- platform-specific automatic setup is committed only when the app-generated or documented TOML shape is confirmed;
- no copied `AGENTS.md` or duplicated skills.
