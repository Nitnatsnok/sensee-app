= ADR коллекция клиента Sensee

Этот каталог содержит architecturally significant decisions для клиентской части `Sensee`.

ADR используются для решений, которые:

* влияют на модульную структуру клиента;
* влияют на quality characteristics;
* задают важные границы между domain, feature, navigation и infrastructure;
* требуют явной фиксации rationale, альтернатив и последствий.

== Соглашения по ведению ADR

* Каждый ADR несёт: `Статус`, `Дата`, `Ответственные`, `Драйверы решения` (со ссылкой на quality goals `QG-*` из `arc42/01` и/или change scenarios `CS-*`/`FS-*` и quality attributes из `arc42/10`), `Контекст`, `Решение`, `Альтернативы`, `Последствия`.
* `Последствия` маркируются как `(реализованные)` — наблюдаемая принятая цена — или `(ожидаемые)` — предсказание; смешивать их нельзя.
* Статусы: `Proposed` → `Accepted`. Набор ADR держится минимальным: одно цельное решение — один ADR, без дробления. Продуктовая модель — единый `ADR-001`. Нумерация сквозная.
* В ADR фиксируются только важные, дорогостоящие, рискованные или архитектурно масштабные решения, затрагивающие структуру, границы или quality attributes системы; локальные решения документируются рядом с блоком. Документационно-процессные политики (например, ведение planned-разрывов) ADR не являются и живут рядом с артефактом, которым управляют — политика planned-backlog: в `docs/evolution-backlog.adoc`.
* Решение не описывается в runtime/building-block view как реализованное, пока его статус не `Accepted` и оно не подтверждено кодом.
