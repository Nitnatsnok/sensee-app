= ADR коллекция клиента Sensee

Этот каталог содержит архитектурно значимые решения для клиентской части `Sensee`.

ADR используются для решений, которые:

* влияют на модульную структуру клиента;
* влияют на качественные характеристики;
* задают важные границы между domain, feature, navigation и infrastructure;
* требуют явной фиксации обоснования, альтернатив и последствий.

== Соглашения по ведению ADR

* Каждый ADR несёт: `Статус`, `Дата`, `Ответственные`, `Драйверы решения` (quality goals `QG-*` — из `arc42/01`; scenarios `US-*`/`CS-*`/`FS-*` — usage/change/fault — и quality attributes из `arc42/10`), `Контекст`, `Решение`, `Альтернативы`, `Последствия`.
* `Последствия` маркируются как `(реализованные)` — наблюдаемая принятая цена — или `(ожидаемые)` — предсказание; смешивать их нельзя.
* Статусы: `Proposed` → `Accepted`; терминальные — `Deprecated` (решение больше не действует, замены нет), `Superseded by ADR-NNN` (заменено новым ADR) и `Rejected` (предложение рассмотрено и отклонено). Принятый ADR неизменяем по существу — правки опечаток и ссылок допустимы, но вывод и последствия не переписываются: чтобы изменить или отменить решение, создаётся новый ADR, который supersede-ит прежний, а прежний помечается `Superseded by ADR-NNN` со ссылкой на замену. Так сохраняется история и трассировка разворотов: набор `Accepted` остаётся достоверным срезом на момент написания.
* Набор ADR держится минимальным: одно цельное решение — один ADR, без дробления. Продуктовая модель — единый `ADR-001`. Нумерация сквозная, номера не переиспользуются.
* В ADR фиксируются только важные, дорогостоящие, рискованные или архитектурно масштабные решения, затрагивающие структуру, границы или quality attributes системы; локальные решения документируются рядом с блоком.
* Решение не описывается в runtime/building-block view как реализованное, пока его статус не `Accepted` и оно не подтверждено кодом.
