= ADR-004: FSRS — единственный источник расписания; возврат карточки в сессию как presentation-проекция
:revdate: 2026-05-15

Статус:: Accepted
Дата:: 2026-05-15
Ответственные:: Konstantin Apukhtin
Драйверы решения:: Reliability (arc42/10, quality attribute «Надёжность»: не допускать смысловой порчи review-состояния), Functional Suitability (QG-1: связный учебный сценарий), Maintainability (QG-3: алгоритм повторения не размазан по presentation)

Контекст::
Practice-сессия должна доучивать карточку в пределах одной сессии (карта, на которую ответили `Again`/`Hard`, обязана вернуться ещё раз), при этом wall-clock внутри сессии ≈ 0: реальные due-времена внутри сессии никогда не наступают. Нужно решить, кто владеет планированием и как организовать внутрисессионный повтор, не заводя второй планировщик и не искажая FSRS-состояние. Дополнительно: штатное поведение многих FSRS-обвязок отправляет `New + Good` сразу в `Review`, минуя learning-steps.

Решение::
FSRS (`FsrsScheduler`) — единственный источник расписания. Возврат карточки в текущую сессию — это **проекция presentation-слоя**: очередь сессии хранит *показы* (`presentationKey`), а дистанция повторного показа проецируется из `srs.scheduledInterval` (`NEAR_GAP`/`FAR_GAP`), потому что литеральные due-времена при elapsed≈0 не наступают. Карта покидает сессию только когда FSRS перевёл её в `Review`; до этого (`Learning`/`Relearning`) возвращается в очередь, с ограничением `MAX_PRESENTATIONS_PER_CARD`. Чтобы это было корректно, `New`-карта проходит через тот же learning-step путь, что и `Learning` (`FsrsScheduler.scheduleCard`: `New, Learning -> scheduleLearningCard`).

Альтернативы::
* Session-only re-show: держать «доучиваемые» карты в чисто сессионной очереди, не трогая FSRS. Отклонено: повторный показ уже выпущенной в `Review` карты делает следующий рейтинг разрушающим Review-re-review при elapsed≈0 дней (порча difficulty/stability).
* Второй внутрисессионный планировщик / кастомная learning-очередь поверх FSRS. Отклонено: два источника правды о расписании — главный риск смысловой порчи и неподдерживаемости.
* Оставить штатное `New + Good -> Review`. Отклонено: новая карта после одного верного ответа улетала бы на дни, learning-steps не работали, in-session recycle для `Good` был невозможен.

Последствия (реализованные)::
* App-wide изменение spaced-repetition семантики: `Good` на новой карте больше не планируется на дни после одного ответа — `New` идёт через learning-steps (FSRS-with-learning-steps / Anki-поведение). Это сознательно принятая цена, не побочный эффект.
* Сознательное отклонение от штатного поведения FSRS-обвязки должно отслеживаться при обновлении алгоритма (риск регресса при upstream-изменениях).
* Планирование имеет единственную точку входа в learning-step: `New` и `Learning` идут одним путём `scheduleLearningCard`; параллельного per-state планирования (`scheduleNewCard`/`scheduledNewCardData`/`scheduledLearningCardData`/`hardLearningInterval`) в модели нет.
* Presentation никогда не владеет расписанием: `DeckPracticeLogic` инспектирует уже посчитанный `ReviewOutcome.srs` (practice-owned результат `submitReview`), только проецирует очередь.
* `practice/domain` — лист над `srs.core`: `PracticeReviewRepository.submitReview` возвращает practice-owned `ReviewOutcome` (`SrsCardSnapshot`), а не `library.domain.Card`; callerы, которым нужен `Card`, ре-проецируют через `library`. Ребро `practice/domain → library/domain` снято и закреплено общим konsist-правилом «feature-`domain` не зависит от чужого feature» (`FeatureLayeringKonsistTest`).
* Due-count для Home подготовлен узким контрактом `DuePracticeRepository` (`countDue(now)`/`observeDueCount(now)`) по `sense_id`; impl в `practice/data` поверх таблицы practice SRS (тот же due-предикат, что и у списка due-карт). Ребро `practice/domain → library/domain` снято, поэтому потребитель сможет показать due-count, не вытягивая `library` (страж — общее `FeatureLayeringKonsistTest`: feature-`domain` не зависит от чужого feature). Само подключение Home к этому шву отложено вместе с due-сессией по запросу (`EB-3`): контракт и страж готовы, потребитель ещё не подключён.

Последствия (ожидаемые)::
* Поведение алгоритма проверяемо изолированно (`shared/srs/*` + `FsrsSchedulerTest`), не смешиваясь с Compose UI.
* Любой новый тип сессии (due-сессия Home, подмножество Library) переиспользует тот же единственный планировщик без дублирования логики поверх SRS по `sense_id`.
