= Представление поведения системы

Раздел намеренно разделяет реализованные сценарии поведения и планируемую продуктовую эволюцию. Это позволяет держать в поле зрения продуктовый приоритет Sensee, не описывая ещё не реализованные расширения как уже работающее поведение. Единственный раздел без реализованного содержания — `Home` (отображает `UnimplementedScreen`).

== Реализованный сценарий 1. Запуск приложения и открытие основного shell

1. Пользователь запускает Android, Desktop, Web или iOS-приложение.
2. Платформенный entrypoint создаёт `PlatformEnvironment` и вызывает `createAppRoot(...)`.
3. `createAppRoot(...)` поднимает `AppGraph` и создаёт `RootComponent`. `RootComponent` сразу запускает app-scoped `PreloadAppStartupUseCase` как safety net для тёплого восстановления: прогреваются `GrammarLabelsProvider` и `TaxonomyInvariantsProvider`, результат запоминается на уровне `shared/grammar/data`.
4. `RootComponent` инициализирует стек Decompose. Стек сохраняется (`screenConfigSerializer`): на холодном старте (нет сохранённого состояния) `initialConfiguration` — `StartupConfig`; при наличии сохранённого стека он восстанавливается как есть, включая deep-target `PrimaryShellConfig(target = …)`, минуя splash.
5. `App(rootComponent)` отображает `RootScreen`.
6. На холодном старте `RootScreen` получает `StartupComponent` и показывает splash, пока `DefaultStartupComponent` запускает тот же `PreloadAppStartupUseCase`; состояние явно переходит в `StartupState.Loaded` или `StartupState.Failed`, retry повторяет preload.
7. После `StartupState.Loaded` `StartupComponent` вызывает `onFinished`, а `RootComponent` открывает основной shell через бизнес-конфигурацию `HomeConfig.Home`.
8. `RootScreen` получает `PrimaryShellComponent` из child stack.
9. `PrimaryShellComponent` создаётся из root `PrimaryShellConfig(target = HomeConfig.Home)` и внутри выбирает `PrimarySectionConfig.HomeSection()` как initial config; `PrimaryShellScreen` показывает базовую primary navigation shell.
10. Раздел `Home` (ещё без реализованного содержания) отображает общую заглушку дизайн-системы `UnimplementedScreen`; остальные разделы показывают свой реализованный срез.

== Реализованный сценарий 2. Прохождение карточек в practice deck

1. Навигация открывает `PracticeConfig.DeckPractice` в `PracticeSectionComponent`.
2. `DefaultDeckPracticeComponent` создаёт `DeckPracticeLogic` с `CatalogRepository` и `PracticeReviewRepository`.
3. `DeckPracticeLogic` запрашивает practice deck через `CatalogRepository`, принадлежащий `Library`, и публикует `DataLoadingState`.
4. `DefaultCatalogRepository` получает каталог/колоды на фикстурах через `CatalogRemoteDataSource`, сохраняет `deck`/`deck_membership` (+ флаг `subscribed` на `deck`) через `CatalogLocalDataSource` (контент смыслов — в таблице `sense` через `lexicon`), а practice data layer подготавливает SRS-состояние через `PracticeSrsStorage`.
5. `DeckPracticeScreen` отображает верхнюю карточку, индикатор прогресса и набор управляющих действий через `shared/ui/learning-deck`.
6. Карточка в UI сохраняет раздельные учебные смыслы: `front`, `back`/meaning, example, transcription и review state не превращаются в один текстовый payload.
7. Пользователь может:
* перевернуть карточку tap'ом или кнопкой `Flip`;
* выполнить swipe жестом;
* инициировать программный swipe кнопками действий;
* использовать клавиатуру на Desktop/Web;
* откатить последний swipe через `Undo`.
8. `LearningSwipeDeck` обновляет локальное состояние колоды: текущий индекс, swipe progress и историю undo.
9. При review action presentation logic передаёт оценку в repository, а data layer обновляет SRS-состояние.
10. После завершения колоды UI показывает `emptyContent` с возможностью откатить последний swipe.

== Реализованный сценарий 3. Что пока не происходит в основном пользовательском потоке

В текущем practice-сценарии пока не происходит:

* обращения к live backend;
* production-аутентификации, синхронизации и полноценного серверного профиля;
* серверной AI-оркестрации.

Сетевой слой, локальное хранение, secure storage для provider-ключей и SRS уже подключены к текущему срезу, но через инфраструктуру на фикстурах и локальную data orchestration.

== Основной продуктовый сценарий. Внесение слова или выражения и разделение смыслов

Статус:: реализованный срез (capture, captured deck projection, lemma grouping); verification-seam реализован, DI-bound и подключён к живому capture в двух узких ролях (pre-AI grounding в prompt, silent post-AI фильтр качества примеров); planned — UI-навигация по family/detail, курирование и выбор form cards при добавлении

На уровне продуктового приоритета Sensee в первую очередь строится не вокруг review, а вокруг внесения и структурирования лексического материала. Раздел `Vocabulary Editor` реализует capture-вертикаль: `DefaultVocabularyEditorSectionComponent` содержит `VocabularyCaptureComponent`/`VocabularyCaptureScreen`, а не заглушку.

Реализованное поведение:

* ввод короткий: одно поле, язык ввода определяется автоматически (`en`/`ru`);
* перед обращением к AI use-case зовёт verifier и строит pre-AI grounding: `EnrichmentGroundingBuilder.toEnrichmentGrounding()` фильтрует наблюдения по `usableAsLlmContext`, кладёт результат в `EnrichmentRequest.grounding`, а `GroundingModifier` рендерит его в prompt; это работает и для обычного capture, и для пути «дополнить ассистентом». Недоступный verifier деградирует штатно — capture идёт без grounding;
* enrichment идёт через единый `SuggestVocabularySensesUseCase` и provider-agnostic границу AI-интеграции: сначала курированное покрытие с бэкенда, затем LLM при настроенном ключе; маппер `vocabulary-editor/domain` (`mapping`) приводит ответ к центральному `Sense`, а Vocabulary Editor оборачивает его в `CaptureSense` для выбора;
* после маппинга enrichment → `Sense` use-case прогоняет один опциональный silent `ExampleQualityChecker`-вызов на каждый пример из `Sense.contextualApplications`: пример отбрасывается только при `Error` и список никогда не опустошается (подтверждённый смысл сохраняет ≥1 пример — инвариант модели). Недоступный или незаведённый checker оставляет примеры без изменений, UI-сигнала нет;
* поток одностраничный: пользователь мультивыбором отмечает смыслы, которые хочет добавить, и/или добавляет свой смысл вручную;
* опциональное действие «дополнить ассистентом» не меняет правило подтверждения: выбранный пользователем смысл становится подтверждённым;
* подтверждённые `Sense` сохраняются через `SenseWriteRepository` (`WriteIntent`) в единственную таблицу `sense` (`lexicon`); статус — per-sense `Draft`/`Confirmed`, идентичность — стабильный `sense_id`; `library` читает наружу через `SenseReadRepository`;
* `SenseCatalogProjection` проецирует Confirmed Personal смыслы в captured deck (одна карта на смысл) и группирует siblings по `lemma_key`; авто-генерация form-variant cards для неправильных глаголов убрана — это станет явным выбором пользователя при добавлении (схема id `${sense_id}:form:…` зарезервирована под них);
* после confirm каждый сохранённый смысл best-effort индексируется для «похоже»: `ConfirmSensesUseCase` зовёт `EmbeddingPort.embed` (вектор от `AiEmbeddingClient`, OpenAI `/v1/embeddings` своим путём — не на enrichment-wire), вектор пишется в `sense_embedding` после коммита смысла, вне write-транзакции; сбой, офлайн или отсутствие ключа не блокируют подтверждение (similar-sense выбор пользователя — навесное). Покрытие следует владению: `claim` тоже индексирует свою копию, а подписанные Service-зеркала — нет (см. Библиотеку каталога ниже).

Планируемое: UI-навигация по семье леммы, полноценные detail-экраны и курирование derived cards. Решение — ADR-001; граница AI-интеграции — ADR-005; граница lexical verification — ADR-007. Пошаговое поведение — `docs/scenarios/vocabulary-capture.feature` (реализованные сценарии помечены `@implemented`, планируемые — `@planned`); схемы — `docs/c4/`; доменные типы — `shared/lexicon/domain` и `shared/feature/vocabulary-editor/domain`.

== Реализованный срез и планируемое курирование. Библиотека каталога

Статус:: реализованный срез (`Library` Home: каталог + подписка на сервисный набор; read-only `DeckDetail`: просмотр карточек собственного и сервисного набора без записи, с явным добавлением сервисного набора с экрана); planned — курирование колод, `LemmaDetail`, claim части набора

Library — владелец каталога лексического материала и колод (`CatalogRepository`/`CatalogAdoptionRepository`/`ClaimRepository` в `shared/feature/library/domain`, реализация — `library/data`); practice выступает read-only потребителем курируемых Library колод (ADR-001). Пошаговое поведение зафиксировано в `docs/scenarios/library.feature` (реализованные сценарии помечены `@implemented`, планируемые — `@planned`).

Реализовано (`LibraryHomeLogic`/`DefaultLibraryHomeComponent`/`LibrarySectionScreen`, `LibraryDeckDetailLogic`/`DefaultLibraryDeckDetailComponent`/`LibraryDeckDetailScreen`):

1. Пользователь открывает раздел `Library`; `LibraryHomeLogic` загружает связанный (отфильтрованный до собственного материала) каталог и список сервисных наборов для подписки.
2. Пользователь подписывается на сервисный набор целиком: смыслы приходят как зеркало (`origin=Service`), практикуются по `sense_id` и обновляются ре-синком по `source_ref`. Подписку можно отменить (unsubscribe). Производная captured-колода Personal-смыслов принадлежит пользователю. `claim` отдельного смысла в детачнутую Personal-копию реализован репозиторием (`ClaimRepository` + `copySnapshot`), его UI — planned; копия индексируется для «похоже» через `EmbeddingPort.embed` после коммита (best-effort). Подписанные Service-зеркала **не** эмбеддятся: similar-sense сравнивает собственный материал пользователя, поэтому покрытие следует владению (`claim`), а не членству (subscribe) — ADR-008.
3. Пользователь открывает набор из списка (`LibraryConfig.DeckDetail`): `LibraryDeckDetailLogic` через `CatalogRepository.previewDeck` проецирует карточки read-only, не записывая ничего — собственный/captured набор читается локально, сервисный проецируется из remote без `ingestDeck` (`toPreviewDeckWithCards`). Карточки рендерятся общим design-system `SenseeSenseCard`. Для сервисного набора показано явное действие «Добавить набор» (`adopt`/subscribe) — единственный путь, который пишет в хранилище.
4. Список колод и `DeckDetail` живут в адаптивном двухпанельном layout: секция — Decompose `ChildPanels` (`appChildPanels`), экран — `AppChildPanels` из `shared/ui/adaptive`. На широком экране (list-detail) обе панели рядом, выбранная колода подсвечена; на компактном — по одной с переходом и системным back, закрывающим деталь. Режим (`SINGLE`/`DUAL`/`TRIPLE`) ведётся от `contentPresentation` — тот же паттерн, что в Profile. Третья панель деталей карточки — planned.

Планируется:

5. Третья панель деталей карточки поверх двухпанельного layout (supporting-pane на широком экране, overlay/sheet на компактном) — `appChildPanels`/`AppChildPanels` уже поддерживают 3-pane.
6. Drill: `LemmaDetail(lemmaKey)` показывает сегрегированные `Sense` семьи леммы с переводами, `ContextualApplication`, структурными grammar cues и производными карточками (entry-агрегат растворён — пивот идёт по `lemma_key`-группе).
7. Правка своей карточки открывает прямую ссылку в `Vocabulary Editor` на экран правки соответствующего смысла/`lemma_key`-группы (тот же поток уточнения, что и ввод; цель ссылки — EB-7). Та же точка входа доступна из карточки practice.
8. Удаление карточки убирает её из каталога и всех колод, но сохраняет confirmed `Sense` в сторе.
9. В `DeckDetail(deckId)` пользователь курирует колоды: одна карточка может входить в несколько колод (many-to-many); удаление из одной колоды не затрагивает другие и каталог.
10. Частичное добавление сервисного набора; запуск practice из курируемой колоды/подмножества открывает `PracticeConfig.DeckPractice`; курирование остаётся в Library, practice его не владеет.

== Планируемый сценарий. Доработка practice: наполнение карты, detail и локальные настройки

Статус:: planned

Доработка поверх реализованного practice-среза. Пошаговое поведение зафиксировано в `docs/scenarios/practice-deck.feature` (сценарии с тегом `@planned`).

1. Карта остаётся лёгкой (recognition): при `practiceFront=English` обратная русская сторона показывает контекст без пилюль-заглушек; при `practiceFront=Russian` слово скрыто пилюлями.
2. Перевод контекстного предложения показывается по тапу (`contextTranslation=on-tap` по умолчанию), а не постоянно.
3. Транскрипция показывается на английской стороне по настройке `showTranscription`; для этого в модель карты добавляется поле транскрипции (сейчас настройка есть, поля нет — сознательный разрыв).
4. При `practiceFront=Russian` и `answerInput=typed` пользователь вводит ответ в группу пилюль для самопроверки; при `answerInput=off` доступен только flip.
5. Detail-панель — хаб исследования: полный `Sense` (переводы, контексты с предлогом/коллокацией, explanation, grammar cues с описаниями), связанные словоформы (формы неправильного глагола, производные части речи), семья леммы и связанные грамматические правила.
6. Из detail можно выбрать часть связанных карточек и добавить их в курируемую Library колоду; курирование остаётся ответственностью Library.
7. Справка объясняет процесс (свайпы↔рейтинги, flip / tap-to-flip, режим заглушек и typed-input, перевод по тапу), а не только глоссарий меток.
8. Кнопка `settings` в practice открывает отдельный экран только со связанными с практикой настройками; полный набор настроек живёт в разделе `Profile`.

Пользователь открывает `Profile`; раздел показывает меню `ProfileHome` с группой видимых категорий настроек. `ProfileConfig` содержит `Home` и конфигурации категорий (`Settings.App`/`Settings.Learning`/`Settings.Practice`/`Settings.Ai`/`Settings.Experimental`); `DefaultProfileSectionComponent` через `appChildPanels` показывает меню и экран категории рядом на широких экранах, по очереди — на узких. 5. Настройки сохраняются в области `Device` по умолчанию; `UserSettingsScope.User` зарезервирован под будущую per-user синхронизацию; переключатель Device/User не показывается, пока нет авторизации.
6. Account/синхронизация показывают «локальный профиль, вход позже»; `About` показывает версию и ссылки.

== Планируемый сценарий. Домашний дашборд

Статус:: planned

`Home` открывается как стартовый раздел уже сейчас, но его содержание — заглушка. Планируемый `Home` ограничен тремя рабочими блоками. Пошаговое поведение — в `docs/scenarios/home.feature` (`@planned`).

1. `HomeComponent` — `NavigationDispatcher`: дашборд не владеет доменом, показывает агрегаты и уводит в другие разделы через `NavigationDispatcher.open(...)`. `HomeConfig` остаётся `Home`.
2. Блок «Повторить сегодня»: счётчик due-карточек (узкий контракт `DuePracticeRepository` уже реализован; Home транзитивно не видит `library`), прогресс к `dailyGoal`, стрик — рабочий виджет текущего дня (агрегаты, без per-card SRS-метаданных; статистика как экран в `Profile` пока не реализована).
3. CTA «Повторить сегодня» уводит сразу в practice по due-подмножеству; это опирается на сессию практики по выборке — планируемое расширение контракта practice (сейчас practice запускает только готовый `Deck`).
4. Блок «Незавершённый capture»: записи в статусе `Draft` (не подтверждённые), CTA уводит в `Vocabulary Editor` на уточнение; при отсутствии незавершённых блок скрыт. Автоматическая уборка брошенных черновиков по таймстемпу — планируемое (EB-6); промежуточные статусы не планируются (модель остаётся `Draft`/`Confirmed`).
5. «Быстрый ввод» открывает `VocabularyEditorConfig.QuickCapture` (authoring-first, ADR-001).

== Реализованный сценарий 4. Распространение навигации чистыми конфигурациями

1. Источник навигации вызывает `NavigationDispatcher.open(config)` с сериализуемым `ScreenConfig`.
2. Локальный host-компонент пытается обработать config своим `NavigationDispatcher`.
3. Если config не принадлежит текущему host, навигационный запрос поднимается по цепочке `local -> parent`.
4. `PrimaryShellComponent` выбирает нужный раздел для `HomeConfig`, `PracticeConfig`, `LibraryConfig`, `VocabularyEditorConfig` или `ProfileConfig`.
5. Если основной shell ещё не открыт, `RootComponent` кладёт полученную бизнес-конфигурацию в свой stack и создаёт `PrimaryShellComponent` с этим target.
6. Если основной shell уже открыт, `RootComponent` переносит существующий `PrimaryShellComponent` наверх и передаёт исходную бизнес-конфигурацию внутрь.
7. `PrimaryShellComponent` уже на своём уровне решает, переиспользовать section component для home-config или пересоздать section component для target-конфигурации.
8. Обратная навигация остаётся отдельным вызовом `NavigationDispatcher.back()` и возвращает результат обработки через `NavigationRequestStatus`.

Реализованная web-навигация (`JS`/`Wasm`)::

На `JS`/`Wasm` активный путь nav-дерева проецируется в историю браузера как производный URL (`withWebHistory`). URL строится из текущего состояния навигации; входом он становится только при разовом разборе прямой ссылки на холодном старте и при кнопках назад/вперёд браузера.

1. Активная секция отражается URL уровня секции: `/practice`, `/library`, ... (`WebSectionRoute.pathFor`); кнопка назад браузера не циклит по табам (`PrimaryShell` `enableHistory = false`).
2. Стек внутри секции отражается в истории: при стеке `[Home, DeckPractice]` кнопка назад браузера снимает `DeckPractice` (`DefaultPracticeSectionComponent` `enableHistory = true`).
3. Прямая ссылка на вложенный экран practice при холодном старте восстанавливает вложенную конфигурацию: `/practice/deck/d1?focus=c9` → `WebSectionRoute.landingForPath` → `PracticeConfig.DeckPractice("d1", "c9")`, и после `Startup` стек секции открыт сразу на этом экране (`DefaultRootComponent.deepLinkLanding`).
4. Splash не имеет URL и не попадает в историю: переход на `PrimaryShell` идёт через `replaceCurrent`, а не push.
5. Тёплая перезагрузка минует `Startup`: при том же URL StateKeeper восстанавливает root stack, активная секция и экран берутся из собственного стека `PrimaryShell`.

Вложенная ссылка в `vocabulary` пока разбирается только до уровня секции (`QuickCapture`); полный разбор до целевого экрана редактора — отложенная доработка (см. `docs/backlog/`, EB-7: после растворения entry цель ссылки — `lemma_key`-группа слова). Пошаговое поведение — `docs/scenarios/navigation.feature`.

UI navigation shell показывает разделы `Home`, `Practice`, `Library`, `Vocabulary Editor` и `Profile`. Реализованное содержание есть у Practice (deck/home/card detail), Library (каталог + подписка), Vocabulary Editor (capture) и Profile (настройки + верификация ключа); `Home` пока отображает `UnimplementedScreen`.
