= Требования к качеству

== Дерево качества

Приоритизация качеств ниже опирается на ISO/IEC 25010 и адаптирована к текущему клиентскому срезу репозитория. Для вводного раздела `01_introduction_and_goals.adoc` первичными архитектурными драйверами считаются `Functional suitability`, `Usability`, `Maintainability` и `Portability`; `Reliability` и `Performance efficiency` остаются важными, но поддерживающими качествами текущего среза.

[options="header",cols="1,3"]
|===
|Качество|Смысл для клиента
|Функциональная пригодность (`Functional suitability`)|Клиент должен поддерживать цельные сценарии текущего среза: запуск, переход к `Practice`, работу с карточками и фиксацию review-результатов, capture смыслов через AI/manual path, library adoption и настройки провайдеров без смешивания разных учебных смыслов
|Удобство использования (`Usability`)|Навигация, карточки, capture, library и настройки провайдеров должны оставаться понятными и предсказуемыми на разных платформах; пользователь не должен теряться между разделами, состояниями загрузки и действиями с карточками/смыслами/настройками
|Сопровождаемость (`Maintainability`)|Новые feature-сценарии, возможности с AI-поддержкой, схемы БД и интеграции должны добавляться через существующие модульные границы без широкого переписывания app shell и платформенных точек входа
|Переносимость (`Portability`)|Shared app shell, feature logic и доменные библиотеки должны переиспользоваться между Android, iOS, Desktop JVM, JS и Wasm при локализации platform-specific кода в соответствующих source set'ах
|Надёжность (`Reliability`)|Локальное состояние practice, capture/library/settings, SQLDelight persistence и SRS-review не должны приводить к потере смысловой целостности данных; отказ внешнего live backend или provider API не должен делать текущий реализованный срез непригодным
|Производительность (`Performance efficiency`)|Запуск приложения, открытие разделов и взаимодействие с колодой карточек должны оставаться отзывчивыми на поддерживаемых целевых платформах
|===

Количественные ориентиры (бюджеты текущего среза, проверяются вручную; авто-замер — не подключён):

* PERF-1 — холодный старт до интерактивного `PrimaryShell` (splash ждёт реальный прогрев таксономии времени выполнения, не фиксированную задержку): целевой бюджет ≤ 2 с на эталонном Desktop/Android-устройстве.
* PERF-2 — взаимодействие с колодой (flip/swipe/программный свайп): целевой бюджет 60 fps (кадр ≤ 16 мс) без длительной блокировки UI-потока на эталонных платформах.
* PERF-3 — capture и настройки провайдеров не должны блокировать UI-поток во время AI/TTS-provider calls; offline/manual path должен оставаться доступным без ожидания live backend.

== Ключевые сценарии качества

=== Usage scenarios

[options="header",cols="1,2,2"]
|===
|Идентификатор|Сценарий|Ожидаемая реакция
|US-1|Пользователь открывает клиент на любой поддерживаемой платформе, переходит в нужный раздел и начинает работу с материалом|Поднимается общий `shared/app-shell`, базовая навигация остаётся общей, а feature-границы не зависят от конкретной платформенной оболочки
|US-2|Пользователь вводит слово или выражение и получает AI-подсказки для смыслов, контекстов и грамматических уточнений|Клиент показывает candidate meanings, contextual applications и grammar cues как отдельные сущности, которые можно подтвердить или отредактировать до создания учебных карточек. Покрыто реализованным срезом capture (ADR-005; `docs/scenarios/vocabulary-capture.feature`, `@implemented`)
|US-3|Пользователь проходит practice deck через tap, swipe, keyboard input и undo|Интерактивное поведение остаётся последовательным и не требует platform-specific реализации в самой feature-логике
|===

=== Change scenarios

[options="header",cols="1,2,2"]
|===
|Идентификатор|Сценарий|Ожидаемая реакция
|CS-1|Нужно добавить новый тип упражнения помимо карточек|Новый сценарий упражнения строится поверх существующей модели исходного лексического материала и feature-границ, не превращая карточку в единственный источник правды о смысле
|CS-2|Нужно добавить новый тип grammar cue или contextual annotation|Новая аннотация добавляется как отдельное структурированное доменное понятие, а не как случайный текстовый комментарий внутри значения или примера
|CS-3|Нужно расширить локальное хранилище новой feature-owned SQLDelight схемой или заменить источник на фикстурах реальным backend|Новая схема добавляется в собственный `database-schema` модуль и агрегируется через `shared/database`; live data layer подключается поверх существующих feature/domain/data/network границ без переписывания app shell и навигации
|===

=== Fault scenarios

[options="header",cols="1,2,2"]
|===
|Идентификатор|Сценарий|Ожидаемая реакция
|FS-1|Во время внесения слова AI-enrichment временно недоступен|Пользователь может продолжить ручное внесение материала; неподтверждённые AI-кандидаты не становятся каноническими данными автоматически. Покрыто: деградация является явным состоянием границы AI-интеграции (ADR-005), fixture-реализация работает без ключа
|FS-2|Источник возвращает неоднозначный или частичный набор смыслов, контекстов или грамматических подсказок|Клиент сохраняет candidate state как неполный результат, явно показывает неопределённость и не смешивает частичные данные с подтверждённым содержимым. Покрыто: anti-corruption mapping `EnrichmentSuggestion → MeaningCandidate`, candidate-слой отделён от confirmed (ADR-005)
|FS-3|Live backend или синхронизация недоступны|Локальный client slice остаётся работоспособным в пределах доступного сценария, а границы между локальными данными, неподтверждёнными кандидатами и серверным состоянием не размываются
|===
