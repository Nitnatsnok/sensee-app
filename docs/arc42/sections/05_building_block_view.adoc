= Представление строительных блоков

== Уровень 1 — Клиентское приложение в целом

Мотивация::
Клиент должен оставаться понятным, продуктово цельным и модульно прозрачным: по коду должно быть видно, что уже работает, что переиспользуемо, а что только подготавливается к дальнейшему росту.

Этот раздел сознательно описывает прежде всего реализованные строительные блоки текущего клиентского среза. Планируемый authoring-first сценарий и связанные продуктовые решения зафиксированы отдельно в `09_architecture_decisions.adoc` и ADR-коллекции.

Для структурного разбора используются `LikeC4 view` `containers`, `capability_map`, `feature_practice`/`feature_vocabulary`/`feature_library`, `integration_seams`, `database_aggregation` и `primary_navigation_shell` в `docs/c4/`. Модель выражает уровни C4 вложенностью (System → Container → Component): `index` даёт контекст, `containers` — контейнерный уровень, `feature_*` — компонентный разбор разделов. Для одного KMP-клиента без отдельных сервисов времени выполнения такая декомпозиция полезнее искусственной.

|Practice Database Schema|`shared/feature/practice/database-schema` хранит SQLDelight-схему practice-карточек и SRS-состояния
|Shared Settings|`shared/settings/domain`, `shared/settings/data` и `shared/settings/database-schema` задают типизированное хранилище пользовательских настроек по категориям
|Reusable UI|`shared/ui/design-system`, `shared/ui/adaptive` и `shared/ui/learning-deck` поставляют нейтральные UI-примитивы; `shared/ui/sense-card` — общая богатая карточка смысла (зависит от `lexicon`/`grammar` domain), используемая разделами `Vocabulary Editor` и `Library`
|Core Runtime|`shared/core/decompose` задаёт инфраструктуру компонентов и навигации, `shared/core/presentation` — общие presentation states, `shared/core/compose` — переиспользуемые Compose-утилиты; DI собирается Metro-графом `AppGraph` в `shared/app-shell`
|Client Integration Foundations|`shared/database`, `shared/core/network`, `shared/core/mock-backend` и `shared/core/observability` предоставляют хранение, `HttpClient` boundary, транспорт на фикстурах и границу runtime diagnostics для текущих сценариев
|SRS Libraries|`shared/srs/*` содержат domain/engine/FSRS библиотеки, которые используются practice data flow для планирования повторений
|AI Enrichment Boundary|`shared/ai/*` — `core` (provider-agnostic boundary contract + request/response extension points: `EnrichmentRequestModifier`, `AiEnrichmentExtension`), `curated-enrichment` (курированное покрытие, отдаётся бэкендом по HTTP), `llm` (LLM-провайдеры, schema из таксономии времени выполнения), `integration` (curated-first routing + DI композиция). Anti-corruption граница для вертикали ввода (ADR-005, ADR-006). Тот же шов несёт второй контракт — embedding: `core` `AiEmbeddingClient`, `llm` `LlmAiEmbeddingClient` (OpenAI `/v1/embeddings`), биндинг в `integration`; идёт отдельным путём, вектор не на enrichment-wire
|Lexical Verification Boundary|`shared/verification/*` — `core` contracts, `sensee-curated` backend-served reference providers (frequency/CEFR/senses/family по HTTP), network adapters, `database-schema` L2 cache и `integration` aggregator. Сам seam реализован, DI-bound и подключён к живому capture в двух узких ролях: pre-AI grounding (`SuggestVocabularySensesUseCase` зовёт verifier до AI, `EnrichmentGroundingBuilder.toEnrichmentGrounding()` фильтрует по `usableAsLlmContext` и кладёт результат в `EnrichmentRequest.grounding`, `GroundingModifier` рендерит его в prompt) и post-AI silent example-quality (опциональный `ExampleQualityChecker` отсеивает пример только при `Error`, никогда не опустошая список). Деградация штатная: недоступный verifier/checker оставляет capture работать без grounding и без отсева
|TTS Seam|`shared/tts/*` — `core` contract, `system`/`elevenlabs`/`openai` impl-адаптеры, `playback`, `cache`, `integration` композиция. Та же seam-конвенция, что и AI
|Neutral Grammar|`shared/grammar/domain` и `shared/grammar/data` задают нейтральную грамматическую таксономию, не привязанную к конкретному языку или AI-провайдеру
|===

Важные интерфейсы::
+
[options="header",cols="2,3"]
|===
|Взаимодействие|Описание
|Platform Entry Logic → Shared App Shell|Платформенные launchers создают `PlatformEnvironment` и вызывают `createAppRoot(...)`
|Shared App Shell → Feature Presentation API|`RootComponent` открывает `PrimaryShellComponent`, а `PrimaryShellComponent` создаёт section components через API contracts
|Shared App Shell → Feature Navigation API|Root/primary navigation маршрутизирует `HomeConfig`, `PracticeConfig`, `LibraryConfig`, `VocabularyEditorConfig` и `ProfileConfig`
|Feature Presentation Implementation → Practice/Library Domain|`DeckPracticeLogic` загружает deck через `CatalogRepository`, принадлежащий `Library`, и отправляет review через `PracticeReviewRepository`, не создавая network/database/SRS зависимости напрямую
|Feature Presentation Implementation → Reusable UI|`DeckPracticeScreen` отображает карточки через `shared/ui/learning-deck`
|Library Data → Client Integration Foundations|`DefaultCatalogRepository` получает каталог на фикстурах через `CatalogRemoteDataSource`, сохраняет `deck`/`deck_membership` (+ флаг `subscribed` на `deck`) через `CatalogLocalDataSource` и SQLDelight, а контент смыслов — через `SenseWriteRepository` (`lexicon`)
|Practice Database Schema → Persistence Module|`shared/feature/practice/database-schema` владеет feature-схемой, а `shared/database` агрегирует её в корневой `SenseeDatabase`
|Shared Settings Data → Persistence Module|`shared/settings/data` реализует `UserSettingsRepository` поверх SQLDelight, а `shared/settings/database-schema` агрегируется в `SenseeDatabase`
|Practice Data → SRS Libraries|Practice data layer применяет SRS engine/storage для review state
|Vocabulary Capture -> Lexical Verification Boundary|Подключено в двух узких ролях: provider-agnostic `shared/verification/*` даёт capture pre-AI grounding (verifier до AI → `EnrichmentGrounding` → `EnrichmentRequest.grounding`) и post-AI silent example-quality (`ExampleQualityChecker` отсеивает слабые примеры, не опустошая список). Обе роли деградируют штатно при недоступности источника
|Vocabulary Capture -> AI Enrichment Boundary|Capture получает смыслы (`Sense`, в редакторе обёрнутые как `CaptureSense`) через provider-agnostic `shared/ai/*`, а не через прямой SDK/endpoint; curated coverage отвечает до LLM
|Profile -> AI/TTS Boundaries|Profile проверяет provider keys/model/voice metadata через `shared/ai/*` и `shared/tts/*`, а настройки хранит через `UserSettingsRepository`
|Grammar Domain → Practice/Vocabulary|`shared/grammar/*` задаёт общие `GrammarUnitType`, `GrammarTag` и labels для карточек и смыслов
|Shared App Shell → Core Runtime|App shell использует Decompose и Metro для component graph и root wiring
|Client Integration Foundations → Core Runtime|Network, mock-backend и database зависимости предоставляются через shared DI graph
|===

=== Белый ящик: Practice Domain/Data

Назначение::
Удерживать учебные смыслы practice-сценария отдельно от UI и инфраструктурных деталей.

Содержащиеся строительные блоки:

* `shared/feature/practice/domain`
* `PracticeSessionPolicy`
* `PracticeCardFront`
* `CardReview`
* `PracticeReviewRepository`
* `ReviewOutcome`
* `DuePracticeRepository`
* `shared/feature/practice/data`
* `DefaultPracticeReviewRepository`
* `DefaultDuePracticeRepository`
* `PracticeSrsStorage`
* `shared/feature/practice/database-schema`

Ответственность::
Применять SRS-review, хранить review state/log и отдавать presentation layer правила session behavior. `practice/domain` — лист над `srs.core`: `PracticeReviewRepository.submitReview` возвращает practice-owned `ReviewOutcome` (не `library.domain.Card`), а `DuePracticeRepository` отдаёт due-count по `sense_id`; ребро `practice/domain → library/domain` снято (общее `FeatureLayeringKonsistTest`). Контент deck загружается через `CatalogRepository`, принадлежащий `Library`. Feature-owned SQLDelight schema остаётся в `shared/feature/practice/database-schema`, а runtime-агрегация схемы и platform drivers живут в `shared/database`.

NOTE: Каталог записей и колоды принадлежат `Library`: `CatalogRepository`/`Deck`/`DeckWithCards` в `shared/feature/library/domain` (реализация — `library/data`); practice — read-only потребитель курируемых Library колод, captured-материал — проекция Personal Confirmed смыслов (`SenseCatalogProjection`). Решение — ADR-001.

=== Белый ящик: Lexicon (канонический sense-store) + Vocabulary Editor (authoring)

Назначение::
Удерживать нейтральную каноническую модель лексического материала (`Sense`) и её единственное durable-хранилище (ADR-001, ADR-008) отдельно от UI, write workflow и границы AI-интеграции.

Содержащиеся строительные блоки:

* `shared/lexicon/domain`
* `Sense`
* `SenseId`
* `StoredSense`
* `SenseStatus` / `SenseOrigin`
* `WriteIntent`
* `SenseReadRepository` / `SenseWriteRepository` / `SearchPort` / `LexicalGraphReader` / `EmbeddingPort` (+ `SenseQuery`, `LexicalEdge`, `EmbeddingVector`, `SimilarSense`)
* `isConfirmable` / `requireConfirmable` (confirm-gate)
* `CefrLevel`
* `shared/lexicon/database-schema` (таблицы `sense`, `sense_embedding`)
* `shared/lexicon/data`
* `DefaultSenseRepository`
* `DefaultSenseIdFactory`
* `DefaultEmbeddingPort` (similar-sense, отдельный класс)
* `shared/lexicon/serialization`
* `shared/feature/vocabulary-editor/domain`
* `SuggestVocabularySensesUseCase`
* `ConfirmSensesUseCase` (confirm + best-effort embed)
* `EnrichmentSenseMapper` (`mapping`: AI enrichment → `Sense`)
* `shared/feature/vocabulary-editor/presentation/api`
* `CaptureSense`

Ответственность::
Маппить provider-agnostic AI enrichment в центральный `Sense`; редактор оборачивает его в editor-state `CaptureSense` (`presentation/api`) только для выбора. Запись идёт через `SenseWriteRepository` с явным `WriteIntent` в единственную durable-таблицу `sense`, которой владеет `lexicon` (seam-owned schema, агрегируется в `SenseeDatabase`, ADR-002); идентичность — стабильный `sense_id` (ADR-008). `library` читает через `SenseReadRepository`/`SenseCatalogProjection`. `SuggestVocabularySensesUseCase` дополнительно несёт две узкие роли verification: pre-AI grounding (verifier → `EnrichmentGroundingBuilder` → `EnrichmentRequest.grounding`) и post-AI silent `ExampleQualityChecker`-фильтр примеров (никогда не опустошает список). После confirm `ConfirmSensesUseCase` индексирует каждый смысл для «похоже» best-effort: `EmbeddingPort.embed` (вектор от `AiEmbeddingClient`) пишет `sense_embedding` после коммита смысла, вне write-транзакции; сбой/офлайн/нет ключа не блокируют save. Покрытие следует владению: эмбеддятся capture и `claim` (`library/data`, Personal-копия); подписанные Service-зеркала не эмбеддятся (similar-sense сравнивает собственный материал — ADR-008). Similar-sense выбор пользователя — навесное.

Грамматическая таксономия — нейтральный `shared/grammar/domain`: sealed-типы с `Unknown(id)`-ветками, парные инварианты — `TaxonomyInvariants` времени выполнения, ADR-006.

== Уровень 3

=== Primary Navigation Shell

Статус:: реализованная базовая оболочка

Текущая базовая навигация опирается на:

* `Home`
* `Practice`
* `Library`
* `Vocabulary Editor`
* `Profile`

Важно::
Разделы открываются через сериализуемые config-типы, а не через прямые вызовы Compose UI.

Форма представления::
Один и тот же набор target-экранов отображается разной навигационной оболочкой, выбираемой адаптивно (`selectPrimaryNavLayout`): нижняя панель в компактном окне, вертикальный `navigation rail` в широком окне на `Android`/`iOS`/`Desktop` и горизонтальный top bar в широком окне на `JS`/`Wasm`. Выбор зависит от размера окна и платформы; config-модель при этом не меняется.

NOTE: На следующем уровне детализации стоит отдельно документировать public API модулей `shared/ui/learning-deck`, `shared/feature/practice/domain`, `shared/feature/vocabulary-editor/domain`, `shared/feature/library/domain`, `shared/srs/*`, `shared/ai/*`, `shared/tts/*`, `shared/database` и `shared/core/decompose`. Для текущей фазы достаточно зафиксировать устойчивые модульные границы и реально существующие сценарии.
