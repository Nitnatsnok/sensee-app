[[client-section-building-block-view]]
= Представление строительных блоков

== Уровень 1 — Клиентское приложение в целом

Мотивация::
Клиент должен оставаться понятным, продуктово цельным и модульно прозрачным: по коду должно быть видно, что уже работает, что переиспользуемо, а что только подготавливается к дальнейшему росту.

Этот раздел сознательно описывает прежде всего реализованные строительные блоки текущего клиентского среза. Планируемый authoring-first сценарий и связанные продуктовые решения зафиксированы отдельно в `09_architecture_decisions.adoc` и ADR-коллекции.

Для структурного разбора используются `LikeC4 view` `capability_map`, `shared_modules`, `current_learning_slice`, `database_aggregation`, `prepared_modules` и `primary_navigation_shell` в `docs/c4/`. Основной подход идёт от модулей, возможностей и потоков поведения: для одного KMP-клиента без отдельных сервисов времени выполнения это полезнее, чем искусственная декомпозиция. Дополнительно поддерживаются C4-проекции для внешнего ревью: `reviewer_system_context`, `reviewer_container_overview` и `reviewer_component_slices`; они помогают ревью, но не заменяют основную модель.

Содержащиеся строительные блоки::
+
[options="header",cols="1,2"]
|===
|Строительный блок|Ответственность
|Platform Entry Logic|`apps/androidApp`, `apps/desktopApp`, `apps/webApp` и `apps/iosFramework` (+ Xcode-хост `apps/iosApp`) поднимают нужную среду выполнения, создают `PlatformEnvironment` и передают управление общему app shell
|Shared App Shell|`shared/app-shell` собирает тему, adaptive environment, root component и platform environment
|Feature Presentation API|`shared/feature/*/presentation/api` задаёт контракты компонентов для разделов `Home`, `Practice`, `Library`, `Vocabulary Editor` и `Profile`
|Feature Navigation API|`shared/feature/*/presentation/navigation-api` задаёт сериализуемые `ScreenConfig` для переходов между разделами и будущих deeplink'ов
|Feature Presentation Implementation|`shared/feature/*/presentation/impl` реализует хост-компоненты разделов, базовые экраны, Practice deck, Library catalog/adoption, Profile AI/TTS/App/Learning settings и Vocabulary capture
|Practice Domain/Data|`shared/feature/practice/domain` и `shared/feature/practice/data` задают repository boundary, domain-модель карточек и поток данных на фикстурах
|Practice Database Schema|`shared/feature/practice/database-schema` хранит SQLDelight-схему practice-карточек и SRS-состояния
|Shared Settings|`shared/settings/domain`, `shared/settings/data` и `shared/settings/database-schema` задают типизированное хранилище пользовательских настроек по категориям
|Reusable UI|`shared/ui/design-system`, `shared/ui/adaptive` и `shared/ui/learning-deck` поставляют переиспользуемые UI-примитивы
|Core Runtime|`shared/core/decompose` задаёт инфраструктуру компонентов и навигации, `shared/core/presentation` — общие presentation states, `shared/core/compose` — переиспользуемые Compose-утилиты; DI собирается Metro-графом `AppGraph` в `shared/app-shell`
|Client Integration Foundations|`shared/database`, `shared/core/network`, `shared/core/mock-backend` и `shared/core/observability` предоставляют хранение, `HttpClient` boundary, транспорт на фикстурах и границу runtime diagnostics для текущих сценариев
|SRS Libraries|`shared/srs/*` содержат domain/engine/FSRS библиотеки, которые используются practice data flow для планирования повторений
|AI Enrichment Boundary|`shared/ai/*` — `core` (provider-agnostic boundary contract + request/response extension points: `EnrichmentRequestModifier`, `AiEnrichmentExtension`), `curated-enrichment` (курированное покрытие, отдаётся бэкендом по HTTP), `llm` (LLM-провайдеры, schema из таксономии времени выполнения), `integration` (curated-first routing + DI композиция). Anti-corruption граница для вертикали ввода (ADR-005, ADR-006)
|Lexical Verification Boundary|`shared/verification/*` — `core` contracts, `sensee-curated` backend-served reference providers (frequency/CEFR/senses/family по HTTP), network adapters, `database-schema` L2 cache и `integration` aggregator. Capture использует его до AI как license-gated evidence и после AI как per-candidate snapshots
|TTS Seam|`shared/tts/*` — `core` contract, `system`/`elevenlabs`/`openai` impl-адаптеры, `playback`, `cache`, `integration` композиция. Та же seam-конвенция, что и AI
|Neutral Grammar|`shared/grammar/domain` и `shared/grammar/data` задают нейтральную грамматическую таксономию, не привязанную к конкретному языку или AI-провайдеру
|===

Важные интерфейсы::
+
[options="header",cols="2,3"]
|===
|Взаимодействие|Описание
|Platform Entry Logic → Shared App Shell|Платформенные launchers создают `PlatformEnvironment` и вызывают `createAppRoot(...)`
|Shared App Shell → Feature Presentation API|`RootComponent` открывает `PrimaryShellComponent`, а `PrimaryShellComponent` создаёт section components через API contracts
|Shared App Shell → Feature Navigation API|Root/primary navigation маршрутизирует `HomeConfig`, `PracticeConfig`, `LibraryConfig`, `VocabularyEditorConfig` и `ProfileConfig`
|Feature Presentation Implementation → Practice/Library Domain|`DeckPracticeLogic` загружает deck через `CatalogRepository`, принадлежащий `Library`, и отправляет review через `PracticeReviewRepository`, не создавая network/database/SRS зависимости напрямую
|Feature Presentation Implementation → Reusable UI|`DeckPracticeScreen` отображает карточки через `shared/ui/learning-deck`
|Library Data → Client Integration Foundations|`DefaultCatalogRepository` получает каталог на фикстурах через `CatalogRemoteDataSource`, сохраняет catalog/deck/adoption state через `CatalogLocalDataSource` и SQLDelight
|Practice Database Schema → Persistence Module|`shared/feature/practice/database-schema` владеет feature-схемой, а `shared/database` агрегирует её в корневой `SenseeDatabase`
|Shared Settings Data → Persistence Module|`shared/settings/data` реализует `UserSettingsRepository` поверх SQLDelight, а `shared/settings/database-schema` агрегируется в `SenseeDatabase`
|Practice Data → SRS Libraries|Practice data layer применяет SRS engine/storage для review state
|Vocabulary Capture -> Lexical Verification Boundary|Capture получает verification evidence до AI и snapshots после AI через provider-agnostic `shared/verification/*`
|Vocabulary Capture -> AI Enrichment Boundary|Capture получает `SenseCandidate` через provider-agnostic `shared/ai/*`, а не через прямой SDK/endpoint; curated coverage отвечает до LLM
|Profile -> AI/TTS Boundaries|Profile проверяет provider keys/model/voice metadata через `shared/ai/*` и `shared/tts/*`, а настройки хранит через `UserSettingsRepository`
|Grammar Domain → Practice/Vocabulary|`shared/grammar/*` задаёт общие `GrammarUnitType`, `GrammarTag` и labels для карточек и смыслов
|Shared App Shell → Core Runtime|App shell использует Decompose и Metro для component graph и root wiring
|Client Integration Foundations → Core Runtime|Network, mock-backend и database зависимости предоставляются через shared DI graph
|===

== Уровень 2

=== Белый ящик: Platform Entry Logic

Назначение::
Поднять нужный платформенный runtime и передать управление общему shared UI.

Содержащиеся строительные блоки:

* `apps/androidApp/src/main/.../MainActivity.kt`
* `apps/desktopApp/src/main/.../main.kt`
* `apps/webApp/src/webMain/.../main.kt`
* `apps/iosFramework/src/iosMain/.../MainViewController.kt`
* `apps/iosApp` как Xcode host application

Ответственность::
Создать платформенный context/environment и запустить `App(rootComponent)`.

=== Белый ящик: Shared App Shell

Назначение::
Собрать общий Compose environment и root navigation для всех платформ.

Содержащиеся строительные блоки:

* `App`
* `AppComposeEnvironment`
* `createAppRoot(...)`
* `AppRootFactory`
* `RootComponent` / `DefaultRootComponent`
* `PlatformEnvironment` и platform-specific реализации

Ответственность::
Подготовить root component graph, открыть `PrimaryShellComponent` и управлять базовой навигацией между разделами.

=== Белый ящик: Feature Presentation API

Назначение::
Задать стабильные component contracts между app shell и реализациями разделов.

Содержащиеся строительные блоки:

* `HomeSectionComponent`
* `PracticeSectionComponent`
* `LibrarySectionComponent`
* `VocabularyEditorSectionComponent`
* `ProfileSectionComponent`

Ответственность::
Определить границу контрактов feature-разделов и не смешивать navigation ownership с Compose-реализацией экранов.

=== Белый ящик: Feature Presentation Implementation

Назначение::
Реализовать section host components, базовые экраны разделов и текущий practice deck-сценарий поверх API-контрактов.

Содержащиеся строительные блоки:

* `DefaultPracticeSectionComponent`, `DefaultPracticeHomeComponent`, `DefaultDeckPracticeComponent`, `DefaultCardDetailComponent`
* `PracticeHomeLogic` / `DeckPracticeLogic` / `CardDetailLogic`
* `PracticeHomeScreen` / `DeckPracticeScreen` / `CardDetailScreen`
* `DefaultLibrarySectionComponent`, `DefaultLibraryHomeComponent`, `LibraryHomeLogic`, `LibrarySectionScreen`
* `DefaultProfileSectionComponent` (двухпанельная навигация по категориям), `DefaultProfileHomeComponent` / `ProfileHomeScreen` (меню категорий), `ProfileAiSettingsLogic` / `ProfileAiSettingsScreen` (категория `Ai`), `ProfileSettingsPlaceholderScreen` (заглушка остальных категорий)
* `DefaultVocabularyEditorSectionComponent` (содержит реализованный `VocabularyCaptureComponent`)
* `DefaultVocabularyCaptureComponent` / `VocabularyCaptureLogic` / `VocabularyCaptureScreen` / `SenseSelectionCard`
* `DefaultHomeSectionComponent` / `DefaultHomeComponent` (раздел `Home` пока отображает `UnimplementedScreen`)

Ответственность::
Собрать feature-разделы, связать practice (deck + home + card detail two-pane), library catalog/adoption и profile settings, а также capture-вертикаль с domain/data boundary. Единственный нереализованный раздел — `Home`: он показывает явный `UnimplementedScreen` вместо имитации функциональности.

=== Белый ящик: Practice Domain/Data

Назначение::
Удерживать учебные смыслы practice-сценария отдельно от UI и инфраструктурных деталей.

Содержащиеся строительные блоки:

* `shared/feature/practice/domain`
* `PracticeSessionPolicy`
* `PracticeCardFront`
* `CardReview`
* `PracticeReviewRepository`
* `shared/feature/practice/data`
* `DefaultPracticeReviewRepository`
* `PracticeSrsStorage`
* `shared/feature/practice/database-schema`

Ответственность::
Применять SRS-review, хранить review state/log и отдавать presentation layer правила session behavior. Контент deck загружается через `CatalogRepository`, принадлежащий `Library`, а practice data отвечает за `PracticeReviewRepository` и SRS storage. Feature-owned SQLDelight schema остаётся в `shared/feature/practice/database-schema`, а runtime-агрегация схемы и platform drivers живут в `shared/database`.

NOTE: Каталог записей и колоды принадлежат `Library`: `CatalogRepository`/`Deck`/`DeckWithCards` в `shared/feature/library/domain` (реализация — `library/data`); practice — read-only потребитель курируемых Library колод, захваченный материал добавляется декоратором каталога. Решение — ADR-001.

=== Белый ящик: Lexicon Domain/Enrichment + Vocabulary Editor Data/Schema

Назначение::
Удерживать нейтральную source-of-truth модель лексического материала (ADR-001) отдельно от UI, write workflow и границы AI-интеграции, с устойчивым хранением.

Содержащиеся строительные блоки:

* `shared/lexicon/domain`
* `Sense`
* `LexicalEntry`
* `EntryStatus`
* `LexiconRepository`
* `shared/lexicon/enrichment`
* `shared/feature/vocabulary-editor/domain`
* `SenseCandidate`
* `VocabularyRepository`
* `shared/feature/vocabulary-editor/data`
* `DurableVocabularyRepository`
* `shared/feature/vocabulary-editor/database-schema`

Ответственность::
Маппить provider-agnostic AI enrichment в центральный `Sense`, оборачивать его в `SenseCandidate` только внутри Vocabulary Editor для выбора/verification snapshots, устойчиво хранить и редактировать подтверждённые `LexicalEntry`/`Sense` в `lexical_entry` агрегатной `SenseeDatabase` (feature-owned schema, ADR-002) и отдавать `Library` read-only контракт `LexiconRepository`.

Грамматическая таксономия — нейтральный `shared/grammar/domain`: sealed-типы с `Unknown(id)`-ветками, парные инварианты — `TaxonomyInvariants` времени выполнения, ADR-006.

=== Белый ящик: Shared Settings

Назначение::
Хранить пользовательские настройки как отдельный shared capability, а не как `feature:settings`.

Содержащиеся строительные блоки:

* `shared/settings/domain`
* `UserSettingsRepository`
* `UserSettingsSnapshot`
* `AppSettings`, `LearningSettings`, `PracticeSettings`
* `shared/settings/data`
* `DefaultUserSettingsRepository`
* `UserSettingsLocalDataSource`
* `shared/settings/database-schema`

Ответственность::
Дать типизированный доступ к настройкам по категориям и scope. SQLDelight schema живёт в `shared/settings/database-schema`, `UserSettingsLocalDataSource` изолирует SQLDelight-операции, `DefaultUserSettingsRepository` реализует domain contract, а `shared/database` агрегирует таблицу `user_setting` в общий `SenseeDatabase`.

=== Белый ящик: Reusable UI

Назначение::
Вынести общие UI primitives в независимые модули.

Содержащиеся строительные блоки:

* `shared/ui/design-system`
* `shared/ui/adaptive`
* `shared/ui/learning-deck`
* `LearningSwipeDeck`
* `LearningDeckState`
* `FlippableLearningCard`

Ответственность::
Переиспользоваться между feature-модулями и платформами без привязки к текущему practice screen.

=== Белый ящик: Core Runtime и Client Integration Foundations

Назначение::
Предоставить среду выполнения и инфраструктурные зависимости, не смешивая их с feature UI.

Содержащиеся строительные блоки:

* `shared/core/decompose`
* `shared/core/presentation`
* `shared/core/compose`
* `shared/database`
* `shared/settings/domain`
* `shared/settings/data`
* `shared/core/network`
* `shared/core/mock-backend`
* `shared/core/observability`

Ответственность::
Поддерживать переиспользуемую среду выполнения, хранение и точки интеграции. `shared/database`, `shared/settings/*`, `shared/core/network`, `shared/core/mock-backend` и `shared/core/observability` входят в текущую shared foundation; `shared/database` собирает корневой `SenseeDatabase` из feature-owned и shared-owned схем, а `shared/core/observability` публикует `AppDiagnostics`, logger, crash reporter и analytics tracker с no-op/local/platform defaults. Внешние observability backend-интеграции остаются planned.

=== Белый ящик: SRS Libraries

Назначение::
Хранить отдельный слой библиотек для алгоритмов повторения и связанных моделей.

Содержащиеся строительные блоки:

* `shared/srs/core`
* `shared/srs/engine`
* `shared/srs/fsrs`
* `shared/srs/fsrs-engine`
* `shared/srs/test-kit`

Ответственность::
Дать независимые shared-библиотеки для вычисления расписания повторений. Practice data layer использует их через `PracticeSrsStorage` и SRS engine, не смешивая алгоритм с Compose UI.

== Уровень 3

=== Primary Navigation Shell

Статус:: реализованная базовая оболочка

Текущая базовая навигация опирается на:

* `Home`
* `Practice`
* `Library`
* `Vocabulary Editor`
* `Profile`

Важно::
Разделы открываются через сериализуемые config-типы, а не через прямые вызовы Compose UI.

Форма представления::
Один и тот же набор target-экранов отображается разной навигационной оболочкой, выбираемой адаптивно (`selectPrimaryNavLayout`): нижняя панель в компактном окне, вертикальный `navigation rail` в широком окне на `Android`/`iOS`/`Desktop` и горизонтальный top bar в широком окне на `JS`/`Wasm`. Выбор зависит от размера окна и платформы; config-модель при этом не меняется.

NOTE: На следующем уровне детализации стоит отдельно документировать public API модулей `shared/ui/learning-deck`, `shared/feature/practice/domain`, `shared/feature/vocabulary-editor/domain`, `shared/feature/library/domain`, `shared/srs/*`, `shared/ai/*`, `shared/tts/*`, `shared/database` и `shared/core/decompose`. Для текущей фазы достаточно зафиксировать устойчивые модульные границы и реально существующие сценарии.
