[[client-section-concepts]]
= Сквозные концепции

Companion reference::
Более компактная предметная сводка доменных сущностей и их связей вынесена отдельно в `docs/domain/information-model.adoc`.

== Shared Client Core

* Общий app shell, feature UI и reusable libraries живут в shared KMP-модулях.
* Platform-specific код изолируется в entrypoints, `PlatformEnvironment` и соответствующих source set'ах.

== Module-First Decomposition

* Основной уровень архитектурной декомпозиции в текущем репозитории — модульный, а не layered-диаграмма ради самой диаграммы.
* Отдельно выделены app shell, feature API/impl, reusable UI, SRS и infrastructure modules.

== Feature Module Convention

* Все feature-модули располагаются под `shared/feature/<feature-name>/`.
* Имена feature и модулей пишутся в lowercase kebab-case на уровне директорий и Gradle path segments.
* Подмодули добавляются по необходимости, а не по шаблону: `presentation/api`, `presentation/impl`, `presentation/navigation-api`, `domain`, `data`, `database-schema`.
* `presentation/api` содержит feature-facing UI contracts и может содержать entry config, если внешний клиент у него только один — host, который создаёт feature component.
* `presentation/impl` содержит Compose-реализацию feature и platform-agnostic presentation logic текущего сценария.
* `presentation/navigation-api` считается опциональным выделением и содержит `ScreenConfig`, route contracts и другие navigation entry points, если другие части клиента должны уметь открывать feature без знания её component API.
* `domain` содержит feature-owned бизнес-модель и контракты вроде `PracticeReviewRepository` или `CatalogRepository`.
* `data` реализует repository, remote/local data sources и integration logic.
* `database-schema` выделяется только тогда, когда feature владеет SQLDelight-схемой, которую нужно подключать к общему database-модулю.
* Если feature участвует в общей root navigation Decompose, её внешние config-типы должны быть сериализуемыми и должны собираться в общий serializer boundary под `shared/core/decompose`, чтобы смешанный stack можно было сохранять и восстанавливать единообразно.
* Реализовано: root-стек `DefaultRootComponent` сохраняется через `screenConfigSerializer` (`StartupConfig`/`PrimaryShellConfig` зарегистрированы), поэтому process-death restore возвращает deep-target, минуя splash; app-scoped прогрев таксономии времени выполнения отделён от splash-экрана и повторно страхует тёплое восстановление.
* `domain`, `data` и `database-schema` считаются опциональными для каждой отдельной feature и добавляются только тогда, когда у неё появляется самостоятельная ответственность.

== Decompose Component Boundary

* `RootComponent` задаёт стартовую навигационную границу приложения и открывает `PrimaryShellComponent`.
* `PrimaryShellComponent` владеет базовой primary navigation shell и открывает section components.
* Feature поднимается через host/component contracts, а не напрямую из platform entrypoint.
* Навигация, component capabilities и logic abstractions живут в `shared/core/decompose`.
* `AppComponentContext` сам реализует capability-интерфейсы `NavigationContext`, `ComponentResultContext` и `ScreenConfigSerializationContext`; отдельный контейнер `AppComponentServices` не используется.

== Metro DI

* App-level wiring собирается через `AppGraph` и assisted factories.
* DI используется для стабильных shared-графов и постепенного роста модульности.

== Shared Settings

* Пользовательские настройки реализованы как shared capability в `shared/settings/*`, а не как `shared/feature/settings`.
* `shared/settings/domain` содержит типизированные категории `AppSettings`, `LearningSettings`, `PracticeSettings`, `AiSettings` (провайдер/ключ/модель AI и TTS) и `UserSettingsRepository`; полный набор `UserSettingsCategory` — `App`, `Learning`, `Practice`, `Ai`, `Experimental`.
* `shared/settings/data` реализует repository через `DefaultUserSettingsRepository`, а SQLDelight-доступ вынесен в `UserSettingsLocalDataSource`.
* `shared/settings/data` подключается в app-level DI graph; `DefaultUserSettingsRepository` публикуется как binding для `UserSettingsRepository`, а `UserSettingsLocalDataSource` создаётся через constructor injection.
* `shared/settings/database-schema` владеет таблицей `user_setting`; `shared/database` агрегирует эту schema в общий `SenseeDatabase`.
* UI feature настроек, если появится, должна жить отдельно в `shared/feature/settings/presentation/*` и работать через `UserSettingsRepository`, не владея storage.

== Reusable Learning Deck

* `shared/ui/learning-deck` — ключевой reusable UI primitive текущего среза.
* Deck поддерживает жесты, клавиатуру, программные свайпы и локальный undo.
* Practice feature использует deck как готовый интерактивный строительный блок и не переносит в него repository/network/database/SRS ответственность.

== Product Semantic Segregation

* Sensee проектируется как клиент с AI-поддержкой обучения: будущий AI-слой должен помогать с объяснениями, подсказками, примерами и уточнениями, но не подменять базовую учебную модель.
* Карточка не считается одним текстовым блоком. В текущем practice-срезе отдельно удерживаются `front`, `back`/meaning, example, `unitType`, grammar tags и review state. Поле транскрипции в модели карты пока отсутствует — планируется (см. `docs/backlog/`, EB-5).
* SRS-состояние и история review относятся к процессу повторения, а не к самому значению слова или фразы.
* Будущие AI-артефакты должны добавляться как отдельные доменные понятия, например подсказка, пояснение, сгенерированный пример или подсказка произношения, а не перезаписывать исходные `front`/`back`.
* UI может показывать эти смыслы рядом, но поток данных должен сохранять их происхождение и ответственность.

== Grammar Taxonomy

* Реализованная practice-модель использует нейтральный `GrammarUnitType`.
* Многомерные грамматические признаки представлены как `GrammarTag(category, form)`: например `verb_irregular/infinitive`, `transitivity/intransitive`, `countability/uncountable`.
* Полная текущая таблица unit types, categories и forms зафиксирована в `docs/domain/pos-and-forms.adoc` и отдана mock backend endpoint'ом `practice/grammar/taxonomy`.
* Practice DTO, локальная SQLDelight-схема и UI работают через `unit_type` и `grammar_tags`.

== Lexical Authoring Model

* Источником учебного материала должен быть не набор карточек, а lexical material, внесённый пользователем.
* Базовая цепочка доменных понятий выглядит так: `Lexical Entry` -> `Sense` -> `Contextual Application` / `Grammar Cue` -> `Derived Learning Card`.
* Один lexical entry может иметь несколько senses; один sense может иметь несколько contextual applications и grammar cues.
* Карточки, practice и review являются производными представлениями подтверждённого материала, а не первичной моделью содержания.

== Lexical Verification Seam

* Лексическая верификация — отдельная граница `shared/verification/{core,sensee-curated,free-dictionary,datamuse,languagetool,database-schema,integration}` по тому же seam-конвенциу, что `shared/ai` и `shared/tts`. `core` — провайдер-агностичный контракт без вендорских SDK и feature-домена; sibling-модули — реализации (один адаптер на внешний API; sensee-curated отдаётся бэкендом по HTTP, в этой сборке — мок-бэкендом); `integration` собирает `RoutingLexicalVerifier` (параллельный fan-out, per-provider timeout) и `PersistedCachingLexicalVerifier` (привязанная в DI реализация `LexicalVerifier`).
* Доступность — first-class: `Available`/`Degraded`/`Unavailable` — штатные исходы. Verifier не бросает исключение через границу (структурная отмена пробрасывается, всё остальное оборачивается в `runCatchingCancellable`). Findings/evidence не появляются на отчёте, у которого `availability is Unavailable` — инвариант `LexicalVerificationReport.init` плюс защитные гейты в merge-хелперах не дают тому случиться даже при misbehaving-адаптере.
* Capture использует verifier дважды: первый раз ДО AI (`SuggestVocabularySensesUseCase` собирает evidence для prompt-канала), второй раз ПОСЛЕ AI (`VerifyVocabularySuggestionsUseCase` навешивает per-candidate `SenseVerificationSnapshot`). Persisted material снимок не несёт; объяснимость живёт на уровне candidate-слоя (ADR-001).
* License-aware агрегация — две неотменяемых границы фильтрации: `LicensePolicy.usableAsLlmContext` гейтит, что из evidence уходит в LLM-prompt; `LicensePolicy.storeContentAllowed` гейтит, какие отчёты ложатся в персистентный L2-кэш. Незарегистрированный contributing-источник трактуется как non-persistable (fail-closed). Подробности — ADR-007 (граница) и ADR-009 (двухуровневый кэш).

== Candidate versus Confirmed Data

* AI-enrichment не должен сразу становиться каноническим содержанием.
* Кандидаты смыслов, контекстов и грамматических подсказок должны жить отдельно от подтверждённых данных.
* Подтверждение пользователем является границей между предложением и каноническим лексическим содержанием.
* Это различение нужно для объяснимости и для предотвращения смешивания смыслов при неоднозначных AI-ответах.

== Catalog Ownership and Service Sets

* Каталог записей и колоды принадлежат `Library`; `Practice` только читает курируемые колоды.
* Карточка может принадлежать нескольким колодам (many-to-many); удаление карточки из одной колоды не затрагивает другие и каталог, а удаление карточки сохраняет confirmed lexical material записи.
* Различаются собственный материал пользователя и сервисные наборы (service sets), приходящие через backend-compatible boundary.
* Добавление сервисного набора целиком реализовано: `CatalogAdoptionRepository` (`library/domain`, реализация `DefaultCatalogAdoptionRepository`) помечает колоду через `practice_deck.adopted_at`; помеченная колода читается как `CatalogOrigin.Personal` и становится собственным материалом. Частичное (по карточкам) добавление — планируется (контракт оставляет место под перегрузку `adopt(deckId, cards)`).
* Practice видит только собственный материал: связанный `CapturedCatalogRepository.observeOwnedMaterial()` отдаёт поток из добавленных наборов + производной колоды захваченных слов, но никогда сами сервисные наборы; сервисный каталог приходит из `CatalogMockFixtures` и виден только в `Library`. Синхронизация сервисного кэша вынесена в явный `CatalogRepository.refreshFromRemote()` и не спрятана в побочном эффекте чтения.

== Settings Scope

* Настройки имеют два UI-представления над одним `UserSettingsRepository`: локальный экран практики должен показывать только связанное с практикой подмножество, а раздел `Profile` показывает видимые profile-targets (`App`, `Learning`, `Practice`, `Ai`, `Experimental`).
* Кнопка `settings` в practice top bar скрыта, пока локальный экран настроек не реализован; целевое поведение — отдельный практический экран настроек, не переход в `Profile`. См. `docs/arc42/sections/06_runtime_view.adoc`.
* Объём `Profile` ограничен реализованными категориями `App`, `Ai` и выбором тем в `Learning`; полный экран настроек, About, Account/синхронизация, статистика и data management остаются planned и не имитируются фиктивным UI.
* Storage scope: дефолт `UserSettingsScope.Device`; `User` зарезервирован под будущую per-user синхронизацию, переключатель Device/User не показывается, пока нет авторизации.
* Категория `UserSettingsCategory.Experimental` существует, но не имеет data class и поля в `UserSettingsSnapshot` — это явное planned-состояние.

== Home Aggregation and Ad-hoc Practice Session

* `Home` — стартовый раздел, пока с заглушкой. Целевое поведение: агрегатор поверх остальных, не владеет доменом, показывает агрегаты и уводит через `NavigationDispatcher.open(...)` в конфигурации других разделов. `HomeConfig` остаётся одним `Home`.
* Today-виджет «Повторить сегодня» показывает агрегаты (due count, прогресс к `dailyGoal`, стрик) без per-card SRS-метаданных; статистика как отдельный экран в `Profile` пока не реализована. Это не противоречие: виджет текущего дня и экран статистики — разные ответственности.
* CTA «Повторить сегодня» уводит сразу в practice по due-подмножеству. Это требует сессии практики по выборке: целевой контракт practice расширяется с готовой `Deck` до запроса/подмножества (та же возможность нужна Library для practice по подмножеству). Сейчас Practice запускает только готовую `Deck`; запуск по произвольной выборке остаётся planned-доработкой. См. `docs/backlog/` (EB-3).
* `tapToFlipEnabled` сейчас живёт только в practice UI state — целевое поведение сохраняет его в `PracticeSettings`.
* Транскрипция: `PracticeSettings.showTranscription` существует, но поля транскрипции в модели карты нет — планируется добавить поле; до этого настройка неактивна. См. `docs/backlog/` (EB-5).
* Планируемые practice-настройки: `answerInput` (off/typed; typed имеет смысл только при русской стороне карточки), `practiceFront` override (EN-only/RU-only/mix через `practiceFrontFor`), `contextTranslation` (always/on-tap), реально подключённый `autoPlayAudio`.

== Platform Environment Abstraction

* Платформенные различия сводятся к `PlatformEnvironment` и platform-specific `PlatformContext`.
* Это позволяет держать корневой UI и root wiring в shared code.

== Database Schema Aggregation

* SQLDelight schema ownership остаётся у feature-модулей вроде `shared/feature/practice/database-schema`.
* Shared capabilities, которые владеют не feature-specific state, могут иметь собственные schema-модули, например `shared/settings/database-schema`.
* `shared/database` агрегирует эти feature-owned схемы в корневой `SenseeDatabase` через `sqldelight { databases { register("SenseeDatabase") { dependency(...) } } }`.
* `SenseeDatabaseProvider` и platform-specific `DriverFactory` живут в `shared/database`, поэтому data-модули получают единый database boundary, не владея platform driver logic.
* Такая схема позволяет расширять локальное хранилище по feature ownership, не превращая `shared/database` в место, где вручную сосредотачивается вся предметная SQL-схема.

== Primary Navigation Model

* Реализован базовый `PrimaryShellComponent` с target'ами `Home`, `Practice`, `Library`, `Vocabulary Editor` и `Profile`.
* Каждый раздел имеет собственный набор `ScreenConfig`: `HomeConfig`, `PracticeConfig`, `LibraryConfig`, `VocabularyEditorConfig` и `ProfileConfig`.
* Публичные feature config'и маркируются как `NavigationTargetConfig`; root использует служебный `PrimaryShellConfig(target)` для основной навигационной оболочки, а section stack внутри неё использует служебные `PrimarySectionConfig`, которые маркируются как `HostScreenConfig` и остаются деталью host-реализации.
* Forward-навигация выражается через `NavigationDispatcher.open(config)`. Конкретный host сам решит, как применить config к своему stack.
* Обратная навигация выражается отдельно через `NavigationDispatcher.back()`.
* `NavigationDispatcher.open` возвращает `NavigationRequestStatus.Handled` или `Unhandled`; это статус обработки запроса текущим host, а не результат stack operation.
* `NavigationDispatcher.back` возвращает результат через `onResult(NavigationRequestStatus)`, потому что для back нет config ownership routing, а `Handled` может означать и закрытие экрана, и сознательную локальную обработку вроде confirm dialog.
* Навигация распространяется чистыми config'ами вверх по цепочке host components до первого обработчика.
* Для stack-based host обратная навигация делегируется Decompose `pop`; если `pop` завершился как `NavigationRequestStatus.Unhandled`, `ChainedNavigationDispatcher` автоматически передаёт `back` родительскому dispatcher.
* Root/primary shell components умеют открыть нужный дочерний раздел и передать target config как initial config при первичном создании host, что оставляет тот же механизм пригодным для будущих прямых ссылок.
* `PrimarySectionConfig` без target использует стабильный `instanceKey`, поэтому выбор уже открытого раздела не пересоздаёт section component.
* `PrimarySectionConfig` с target получает новый `instanceKey`, а `PrimaryShellComponent` применяет `bringToFront(recreate = true)` для section component того же класса; поэтому повторное открытие того же target создаёт новый section component instance и не накапливает старые экземпляры этого раздела.
* Для выбора уже открытого раздела без target используется отдельная stack-операция, которая ищет section host по классу config и переносит существующий config наверх.
* Для forward-навигации `onComplete(isSuccess)` прокидывается до Decompose stack operation, поэтому вызывающая сторона может дождаться результата самой навигационной операции, не выбирая тип операции сама.
* Конкретный UI-паттерн может различаться по платформам, но семантика target'ов должна оставаться общей.

== Practice Data Flow

* Deck content для practice приходит из `CatalogRepository`, принадлежащего `Library`; practice не владеет catalog/deck content.
* `PracticeReviewRepository` является границей для отправки review result и обновления SRS-состояния.
* `CatalogRemoteDataSource` получает catalog/deck данные на фикстурах через общий `HttpClient`, предоставленный `shared/core/network`.
* `shared/core/mock-backend` предоставляет mock engine и fixture sets для текущего учебного среза без live backend.
* `CatalogLocalDataSource` и `shared/feature/library/database-schema` используют SQLDelight для catalog/deck/adoption state; `PracticeSrsStorage` и `shared/feature/practice/database-schema` используют SQLDelight для SRS-состояния и review log.
* `shared/srs/*` остаются самостоятельными библиотеками, но текущий practice data flow уже применяет их для планирования повторений.
* `Library` материализует SRS-снимки карточек через `SrsStorage` (контракт принадлежит `Practice`) и переиспользует контракт обогащения (`ai.core` + `lexicon` enrichment) при деривации каталога, поэтому `library/data` статически зависит от `shared/srs/*` и `shared/ai/core`.
* Practice deck может озвучивать текущую карточку через `tts` seam (`Speaker`), не владея синтезом речи; выбор провайдера и ключ остаются в `Profile`/`Settings`.

== Honest Evolution

* Клиент не должен притворяться production-ready продуктом, если текущий сценарий пока работает на фикстурах.
* Документация, LikeC4 и код должны одинаково различать реализованное, подготовленное и планируемое.
* В `LikeC4` это различение выражается тегами `#prepared`/`#future` на элементах и связях, а структура показана через вложенные `containers`, `feature_*` и `deployment`.
