# Лексическая верификация — обзор для людей

Объяснение «почему оно так устроено». Технические детали — в `AGENTS.md`
и ADR'ах, на которые ссылки в конце.

## Что эта граница вообще делает

Когда пользователь добавляет слово в свой словарь, в фоне работает
конвейер: AI-обогащение предлагает смыслы и примеры, **верификация** их
независимо проверяет, а UI показывает финальный результат. Верификация
отвечает на структурные вопросы про лексическую единицу:

- Существует ли такое слово/фраза в английском?
- Какая часть речи / варианты POS?
- Какой CEFR-уровень?
- Какая частотность (Zipf)?
- Какие есть смыслы в словарях?
- Какие у слова «родственники»: phrasal verbs, идиомы, дериваты?
- Правильное ли AI предложение по примеру?

Это всё нужно по двум причинам:

1. **AI ошибается.** Без второго мнения первая же галлюцинация лезет в
   пользовательский словарь как канон. Верификация ловит выдумки до того,
   как они станут frontend-доменом.
2. **CEFR и частотность — пед-сигнал.** Учебнику важно знать, что
   `elucidate` — уровень C1, а не A1; что `the` встречается в 7 раз чаще
   `house`. Это управляет ranking'ом, learning-path'ом, выбором примеров.

Граница оформлена тем же паттерном, что `shared/ai` и `shared/tts`:
`core` несёт провайдер-агностичные контракты, соседние модули — адаптеры
на конкретные источники, `integration` композирует их в `LexicalVerifier`,
который видит фича-код.

## Главная идея — два рода источников, всё по HTTP

На устройстве больше нет предсобранной БД и сторонних корпусов. Всё, что
нужно верификатору, приходит по сети в момент проверки.

```
┌──────────────────────────────────────────────────────────────┐
│ Sensee-curated — наши данные, отдаёт бэкенд                   │
│  - frequency / CEFR / senses / family                         │
│  - сейчас: мок-бэкенд (shared/core/mock-backend),             │
│    редактируемые JSON-фикстуры verification/<facet>.json      │
│  - адаптеры sensee-curated фетчат каталог и кэшируют           │
│  - лицензия: наше, всё разрешено                              │
│  - роль: справочный baseline на покрытых леммах               │
└──────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────┐
│ Network — сторонние HTTP API во время выполнения              │
│  - FreeDictionary (existence/POS), Datamuse (spell-fix),      │
│    LanguageTool (качество примера)                            │
│  - каждый со своим HttpClient, изолирован                     │
│  - gated request-level policy.allowNetwork                    │
│  - роль: спросить внешний источник, когда у нас нет ответа    │
└──────────────────────────────────────────────────────────────┘
```

### Почему бэкенд-доставка, а не предсобранная БД на устройстве

Предсобранная SQLite-БД на клиенте (один `dictionary.db` в classpath) дала бы
offline, но утяжелила бы packaging/asset population, на web держала бы большой
sql.js payload в памяти воркера, а вдобавок тянула бы вендорные лицензии и
build-time populate-машинерию. Поэтому наши справочные данные отдаёт бэкенд
по HTTP. Сейчас это **мок-бэкенд** — имитация будущего реального бэкенда: тот
же `HttpClient`, те же формы ответов, только адрес сменится. Это:

- **работает на всех таргетах одинаково** (HTTP есть везде, отдельный
  bundled dictionary DB не нужен);
- **без вендорной привязки** — держим только своё, licence-clean;
- **редактируется как данные, не как код** — авторский цикл = править JSON-файл
  (см. «Как редактировать»).

Вендор-зависимые источники (WordNet, Wiktionary) сюда не входят — их роль
закрывают наш бэкенд или сторонние онлайн-API.

### Почему network — отдельный род, а не часть нашего бэкенда

FreeDictionary / Datamuse / LanguageTool — это чужие сервисы:

- Request-level `policy.allowNetwork = false` выключает fan-out для
  специальных offline/test-запросов. Пользовательской настройки в клиенте нет:
  если consent на стороннюю обработку понадобится в product flow, он должен
  жить как backend-owned policy.
- Лицензии разнятся и решаются пофлагово: строгий источник может запрещать
  хранение ответа на диске (`storeContentAllowed = false` → только L1).
- Outage у одного API не должен валить остальное — каждый со своим
  `HttpClient`.

Агрегатор `RoutingLexicalVerifier` собирает оба рода поверх
`Set<LexicalEntryLookup>` / `Set<FrequencyProvider>` / etc.

## Хранение наших данных: мок-бэкенд (потом — реальный)

`sensee-curated` отдаёт четыре каталога-фикстуры, по одному на фасет:
`verification/frequency` (лемма → zipf), `verification/cefr` (лемма →
уровень), `verification/senses` (лемма → глоссы), `verification/family`
(head-лемма → юниты). Файлы лежат под
`shared/verification/sensee-curated/src/commonMain/mockFixtures/verification/`,
плагин `sensee.mockFixtures` вшивает их в сборку (нужно для web/wasm, где нет
рантайм-ФС). Адаптер фетчит каталог один раз и кэширует в памяти.

Реальный бэкенд позже будет отдавать те же формы под тем же
`SenseeCuratedSource` — клиентский код не поменяется. Поэтому JSON-фикстура —
это и есть контракт API, который мы экспортируем сами в себя.

## Почему лицензионный барьер — два рабочих флага

`LicensePolicy` в `core/LexicalSource.kt`:

```kotlin
data class LicensePolicy(
    val storeContentAllowed: Boolean = false,
    val usableAsLlmContext: Boolean = false,
    // + maxCacheTtlMillis: Long?, noteIfAny: String? — не флаги
)
```

Два флага — две отдельные точки применения, **не сводимы друг к другу**:

- `storeContentAllowed` — можно ли положить ответ в L2-кэш на диск пользователя
  (ADR-009). Если `false` — едет только в L1 (память процесса).
- `usableAsLlmContext` — можно ли подмешивать в evidence-канал для AI
  обогащения. Sensee-curated — можно; чужой коммерческий gloss — нельзя.

Флаги ортогональны: источник может быть пригоден для LLM, но не для диска.
Sensee-curated — оба `true` (наши данные). Сторонний источник может иметь
`usableAsLlmContext = true` (короткий факт можно отдать LLM), но
`storeContentAllowed = false`, если лицензия не разрешает класть ответ на диск.
Агрегатор к тому же трактует **незарегистрированный** в каталоге источник как
non-persistable (fail-closed), чтобы пробел в каталоге не открыл утечку.

## Как редактировать данные (быстрая шпаргалка)

1. Наши справочные данные: открыть нужный каталог-фикстуру под
   `shared/verification/sensee-curated/src/commonMain/mockFixtures/verification/`
   (`frequency.json`, `cefr.json`, `senses.json`, `family.json`) и
   дописать/исправить запись. Ключи лемм — в нижнем регистре.
2. Curated AI enrichment: по файлу на лемму под
   `shared/ai/curated-enrichment/src/commonMain/mockFixtures/enrichment/`.
3. Пересобрать (codegen вшивает фикстуры в сборку). Consistency-тесты
   (`SenseeCuratedMockFixturesTest`, `CuratedEnrichmentMockFixturesTest`)
   ловят битую форму и не-нормализованные ключи.

Подробнее — `AUTHORING.md`.

## Где что лежит — карта

- `core/` — провайдер-агностичные контракты + `LicensePolicy` +
  evidence-модели. Без зависимостей от dictionary SDK или feature domain.
- `sensee-curated/` — наши справочные данные: HTTP-адаптеры четырёх фасетов,
  кэширующий `SenseeCuratedCatalogs`, `SenseeCuratedSource` дескриптор и
  редактируемые фикстуры-каталоги.
- `free-dictionary/`, `datamuse/`, `languagetool/` — network-адаптеры.
- `integration/` — DI-сборка + `RoutingLexicalVerifier` +
  `PersistedCachingLexicalVerifier`.
- `database-schema/` — SQLDelight-схема **кэша верификации** (это кэш ответов
  verifier'а под `policy + query`, ADR-009 — не справочные данные).
